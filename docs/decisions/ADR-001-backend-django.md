# ADR-001: Бэкенд основного сайта — Django + Django Ninja

**Status:** Accepted
**Date:** 2026-07-30
**Deciders:** Yanislav Pichugin

## Context

Сайту нужен бэкенд: пользователь хочет редактировать портфолио через собственную админку (auth, CRUD, загрузка файлов, БД), а не через правку файлов в git. Кандидаты по исходной задумке — Python (Django) или Go. Одновременно есть желание попробовать оба языка. Ограничение: один разработчик, работа по вечерам, проект должен доехать до продакшена, а не застрять в инфраструктуре.

Отдельно рассматривался вопрос «а нужен ли бэкенд вообще» — для чистого лендинга не нужен, но требование редактируемого через UI портфолио решает вопрос в пользу «нужен».

## Decision

Бэкенд сайта — **Django 5.2 LTS + Django Ninja** (API-слой с pydantic-схемами и автогенерацией OpenAPI). Желание писать на Go удовлетворяется **отдельным сервисом** — uptime-чекером ([ADR-005](ADR-005-uptime-go.md)). Оба языка получают своё место, каждый — там, где сильнее.

## Options Considered

### Option A: Django + Django Ninja

| Dimension | Assessment |
|-----------|------------|
| Сложность | Low — батарейки: ORM, миграции, auth, сессии, media |
| Скорость до MVP | High — CRUD+auth за вечера, а не недели |
| Learning value | Med — Django нов для стека пользователя, но это «ещё один фреймворк» |
| Fit к задаче | High — встроенная админка = запасной редактор контента с первого дня |

**Pros:** Django-админка бесплатно решает «вносить контент», пока своя админка не готова (и остаётся страховкой навсегда); Ninja даёт OpenAPI → генерация TS-типов для фронта; ORM+миграции убирают целый класс ручной работы; зрелая безопасность (CSRF, сессии, rate-limit пакеты).
**Cons:** образ тяжелее Go-бинаря; «магия» фреймворка меньше учит низкоуровневым вещам; два языка в репозитории (python + go) — осознанная плата.

### Option B: Go (chi/echo + sqlc/GORM)

| Dimension | Assessment |
|-----------|------------|
| Сложность | Med/High — auth, миграции, admin, upload — всё руками |
| Скорость до MVP | Low — недели вечеров до первого CRUD с авторизацией |
| Learning value | High |
| Fit к задаче | Med — для CRUD-контента преимущества Go не играют |

**Pros:** один бинарь, минимум памяти, максимум обучения.
**Cons:** высокий риск «застрять в сантехнике» и не доехать до контента; нет готовой админки — до Phase 3 контент вносить нечем; безопасность auth полностью на себе.

### Option C: Без отдельного бэкенда (SvelteKit fullstack + SQLite)

| Dimension | Assessment |
|-----------|------------|
| Сложность | Lowest — один сервис |
| Скорость до MVP | High |
| Learning value | Low — не даёт ни Python, ни Go |
| Fit к задаче | Med — технически всё возможно (form actions, Drizzle, Lucia) |

**Pros:** минимум движущихся частей; самый дешёвый в эксплуатации.
**Cons:** противоречит цели «fullstack на Python/Go» и цели «сайт как демонстрация многосервисной архитектуры»; auth и админку всё равно писать руками; контент-сервис сцеплен с фронтендом.

## Trade-off Analysis

Ключевой конфликт — **обучение vs доставка**. Go-бэкенд максимизирует обучение, но с наибольшим риском для результата: критический путь проекта (контент, админка) ложится на самый медленный вариант. Разделение «Django — там, где нужна скорость и батарейки; Go — на отдельном некритичном сервисе» снимает конфликт: обучение Go происходит на uptime-чекере с маленьким scope, а сайт едет быстро. Option C выигрывает по простоте, но обнуляет половину мотивации проекта.

## Consequences

- Контент можно вносить с первого дня (Django-админка) — своя админка перестаёт блокировать запуск.
- OpenAPI-схема Ninja становится контрактом между api и frontend (генерация типов).
- В репозитории три тулчейна (py/ts/go) — CI разделён по каталогам с `paths:`-фильтрами, это уже заложено в структуре.
- Придётся следить за размером python-образа (multi-stage, `-slim`).
- Ревизит: если api станет тесно (реалтайм, тяжёлые фоновые задачи) — пересмотреть, но для портфолио это маловероятно.
