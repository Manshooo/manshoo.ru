# ADR-003: Рендеринг — гибридный SSR; админка — CSR

**Status:** Accepted
**Date:** 2026-07-30
**Deciders:** Yanislav Pichugin

## Context

SEO — заявленный приоритет: контент должен быть в HTML-ответе, без исполнения JS (Google исполняет JS, Яндекс — ограниченно; полагаться на это не хотим). При этом контент редактируется через админку и должен появляться на сайте **сразу**, без пересборки. Трафик — единицы RPS в худшем случае.

## Decision

Публичные страницы — **SSR** (SvelteKit adapter-node): HTML собирается на сервере из данных api при каждом запросе; полностью статичные страницы (404, будущие /uses и т.п.) — prerender. Раздел `/admin` — **CSR** + `noindex`. Кэширование на прокси — не включаем, пока не понадобится (см. Consequences).

## Options Considered

### Option A: SPA (CSR everything)

| Dimension | Assessment |
|-----------|------------|
| SEO | Low — контент только после JS; для Яндекса риск |
| Сложность | Lowest |
| Свежесть контента | High |

Отклонён: прямо противоречит приоритету SEO.

### Option B: SSG + rebuild-хук

| Dimension | Assessment |
|-----------|------------|
| SEO | High |
| Скорость отдачи | Highest (статика) |
| Свежесть контента | Low/Med — публикация = webhook → CI-сборка → деплой (минуты, зависимость от CI) |
| Сложность | Med — цепочка «админка → триггер → пайплайн» |

**Pros:** идеальная производительность, дёшево хостить.
**Cons:** «нажал Опубликовать — жди пайплайн» ломает UX собственной админки; появляется зависимость публикации от GitHub Actions; предпросмотр черновиков всё равно требует динамики.

### Option C: Гибридный SSR (выбран)

| Dimension | Assessment |
|-----------|------------|
| SEO | High — полный HTML в ответе |
| Скорость отдачи | Med/High — рендер на каждый запрос, но страницы лёгкие, api рядом (docker-сеть) |
| Свежесть контента | High — мгновенная публикация и предпросмотр черновиков |
| Сложность | Low/Med — node-процесс уже заложен в архитектуру (сервис frontend) |

## Trade-off Analysis

Выбор между B и C — это «максимальная скорость отдачи» против «мгновенная публикация + простой пайплайн». При нашем трафике SSR-накладные расходы неощутимы, а UX публикации и предпросмотр черновиков — ежедневно ощутимы. Резерв по производительности остаётся: включить micro-cache (30–60 c) на Caddy для анонимных GET — одна строка конфига, когда/если понадобится.

## Consequences

- Контент из админки виден на сайте мгновенно; `?preview=1` для черновиков работает естественно.
- Frontend-контейнер обязан быть живым для отдачи сайта (healthcheck + restart policy; SSG-вариант деградировал бы мягче) — принято.
- SSR-фетчи к api идут по внутренней docker-сети — быстро и не зависят от публичного TLS.
- sitemap.xml/robots.txt — динамические endpoints frontend'а.
- Ревизит: если появится заметный трафик — micro-cache на прокси; переезд на SSG не потребуется.

## Action Items

1. [ ] Phase 2: server-only `load`-функции для страниц сайта; `export const prerender` для статичных.
2. [ ] `/admin`: `ssr = false`, `noindex`, исключение из sitemap.
3. [ ] Отложенный триггер: строка micro-cache в Caddyfile — закомментированной заготовкой.
