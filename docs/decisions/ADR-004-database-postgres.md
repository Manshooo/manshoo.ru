# ADR-004: БД сайта — PostgreSQL; у uptime-чекера — встроенный SQLite

**Status:** Accepted
**Date:** 2026-07-30
**Deciders:** Yanislav Pichugin

## Context

Два независимых хранилища: (1) контент сайта в сервисе api — профиль, проекты, пользователь админки, медиа-метаданные; (2) история проверок uptime-чекера. Масштаб крошечный (десятки записей контента; сотни тысяч строк истории проверок за годы). Docker-compose уже оркестрирует несколько сервисов, добавление контейнера БД — дёшево.

## Decision

- **api → PostgreSQL 17** (контейнер в compose, volume, ночной `pg_dump`).
- **uptime → SQLite** внутри сервиса (файл на volume, драйвер без CGO).

Сервисы **не делят БД** — общение только через HTTP API.

## Options Considered

### Option A: SQLite для всего

| Dimension | Assessment |
|-----------|------------|
| Простота эксплуатации | Highest — файл, бэкап = копия |
| Возможности | Достаточно для этого масштаба (честно) |
| Ценность как опыт/витрина | Low — «продовый Django на Postgres» ожидаемая связка в резюме |
| JSONB-поля | Есть JSON1, но слабее (индексы, операторы) |

### Option B: PostgreSQL для всего (включая uptime)

| Dimension | Assessment |
|-----------|------------|
| Простота | Med — uptime получает сетевую зависимость от контейнера БД |
| Автономность uptime | Low — чекер должен «стоять на своих ногах» и работать, даже если полсистемы лежит |

### Option C: Раздельно — Postgres для api, SQLite для uptime (выбран)

| Dimension | Assessment |
|-----------|------------|
| Простота | Med/High |
| Автономность uptime | High — ноль внешних зависимостей у сервиса-наблюдателя |
| Fit инструмента к задаче | High — реляционный контент+админка vs журнал одного писателя |

## Trade-off Analysis

Для api Postgres даёт JSONB (поля `stack`, `highlights`, `links` без лишних таблиц), стандартную прод-связку с Django и нулевую вероятность «перерасти SQLite». Цена — один контейнер и bэкап через `pg_dump` — уже заложена в compose-архитектуру. Для uptime всё наоборот: главная добродетель наблюдателя — независимость; встроенный SQLite означает, что чекер жив, пока жив его контейнер. Выбор «каждому сервису — своё хранилище» дополнительно демонстрирует инженерное суждение (это витринный проект).

## Consequences

- Два вида бэкапов: `pg_dump` + копия файла SQLite (один cron, см. [01-architecture.md](../01-architecture.md)).
- В dev Postgres тоже в compose — dev/prod паритет, миграции гоняются одинаково.
- SQLite-драйвер для Go — `modernc.org/sqlite` (без CGO) → образ from distroless, простая кросс-сборка.
- Ревизит: не предвидится; масштаб не вырастет из этих решений.
