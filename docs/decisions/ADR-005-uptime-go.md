# ADR-005: Uptime-чекер — собственный сервис на Go

**Status:** Accepted
**Date:** 2026-07-30
**Deciders:** Yanislav Pichugin

## Context

Нужен мониторинг личных проектов: сейчас azzb.ru, после деплоя — manshoo.ru; алерты о падениях. Параллельно есть цель изучать Go ([ADR-001](ADR-001-backend-django.md) отдал бэкенд сайта Django именно потому, что Go получает этот сервис). В репозитории каталог `uptime/` с собственным Dockerfile и CI-workflow уже заложен — сервис задуман как самостоятельная часть системы. Требуется и интеграция: живые статусы проектов на карточках портфолио.

## Decision

Пишем **свой сервис на Go**: HTTP-проверки, состояние, история в SQLite, Telegram-алерты, JSON API для сайта. Спека — [05-uptime.md](../05-uptime.md). Он же — будущий кейс в портфолио.

## Options Considered

### Option A: Свой сервис на Go (выбран)

| Dimension | Assessment |
|-----------|------------|
| Learning value | High — конкурентность (тикеры/горутины), stdlib http, работа с SQLite, деплой бинаря |
| Scope | Small — реально дописать до v1 за несколько вечеров |
| Интеграция с сайтом | High — свой JSON API, любые бейджи/страницы |
| Функциональность из коробки | Low — всё пишем сами (осознанно) |

**Pros:** идеальный размер учебного Go-проекта; полная свобода интеграции; кейс в портфолио («написал и эксплуатирую свой мониторинг»); лёгкий (distroless-образ в десятки МБ, память — мегабайты).
**Cons:** беднее готовых решений (нет UI, десятков типов проверок); поддержка на себе.

### Option B: Uptime Kuma (self-hosted, готовый)

| Dimension | Assessment |
|-----------|------------|
| Learning value | ~Zero |
| Функциональность | High — UI, куча интеграций, status pages |
| Интеграция с сайтом | Med — есть API/бейджи, но чужой дизайн и лишний сервис-комбайн |

**Pros:** результат за один вечер.
**Cons:** обнуляет учебную цель; тяжёлый node-контейнер ради двух мониторов; «настроил Kuma» — не кейс для портфолио.

### Option C: Внешний сервис (UptimeRobot / healthchecks.io / StatusCake)

**Pros:** ноль эксплуатации, мониторинг «снаружи» (плюс к достоверности).
**Cons:** не «свой сервис» (прямое требование), лимиты бесплатных тарифов, нет учебной ценности. Но идея пригодится: внешний heartbeat как компенсация слепого пятна (см. ниже).

## Trade-off Analysis

Выбор между «функциональность сейчас» (B/C) и «обучение + владение» (A). Поскольку функциональные требования крошечные (2 монитора, Telegram, статусы для сайта), проигрыш варианта A по фичам почти не материализуется, а выигрыш в обучении и витринности — целиком. Риск варианта A — «написал и забросил» — купирован маленьким scope v1 и тем, что сервис немедленно полезен (azzb.ru мониторится с Phase 1).

Отдельно учтено слепое пятно: чекер на том же VPS не увидит падение самого VPS. Компенсация — heartbeat на healthchecks.io (v1.1) и, в бэклоге, вынос чекера на отдельный хост. Вариант B страдал бы тем же.

## Consequences

- Go появляется в проекте на некритичном пути: сайт не зависит от чекера (graceful degradation бейджей).
- Сервис полностью автономен (SQLite, свой конфиг) — переносим на другой хост одним контейнером.
- Все «хотелки» мониторинга (TLS-expiry, инциденты, графики) — наша собственная дорожная карта, добавляем по потребности.
- Поддержка и багфиксы — на нас; принято как часть учебной цели.
